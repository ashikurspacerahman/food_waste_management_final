## Feature: one food image per donation

### Design decisions
* **No migration needed.** The schema already has an image field: `DonationImage(image_id, donation_id, image_url)` (table 9). `image_url` stores the **relative path** (`uploads/food/food_<32 hex>.jpg`). The endpoint keeps exactly one row per donation. No `image_path` column was added and no SQL has to be run.
* Files live in `uploads/food/`. Only the path is in MySQL (no binary data).
* Old behaviour removed: `POST /api/donations.php` used to accept a free-text `imageUrl` from the browser and store it. That is gone (it let a client store arbitrary paths); the path is now only ever generated by the server.

### API contract
* `POST /api/donations.php` — donor only. `multipart/form-data` (or JSON without a photo). Optional file field `image`.
* `POST /api/donations.php?id=<donationId>&action=image` — donor who owns the donation only; donation status must be `draft`, `available` or `requested`. Field `image` required.
* Both return the normal donation JSON; `imageUrl` is the relative path or `null`. Errors are `{ "message": "..." }` with 400/401/403/404/409/413/415/500.

### Server-side rules
* Session + role check (`donor`); ownership checked in SQL (`donor_id = session user`), another donor's donation answers 404.
* Real MIME type via `finfo` on the temp file; only `image/jpeg`, `image/png`, `image/webp`; `getimagesize()` must agree; max 5 MB measured on the real temp file (`413`); max 8000×8000 px; `post_max_size` overflow detected.
* File name = `food_` + 32 random hex chars + extension chosen from the detected MIME type (the uploaded name is never used).
* New file is saved first; if the database step throws, the new file is deleted. On replace, old files are deleted only **after** the transaction commits, only for paths read from that donation's own `DonationImage` rows, and only if the path matches `uploads/food/food_<32 hex>.(jpg|png|webp)` and resolves inside `uploads/food/` (symlinks refused).

### Migration instructions
None. `database/food_waste_management.sql` is unchanged. Existing databases keep working; donations without a `DonationImage` row show the emoji placeholder.

### Display fix (after first look at real photos)
The large photo on the donor/recipient details pages was cropped into a 260 px-high strip (`object-fit: cover`), cutting off the bottom of the picture. `assets/css/dashboard.css` now shows the whole photo there (`.food-thumb--lg.food-thumb--photo`: natural aspect ratio, max height 420 px, `object-fit: contain`). Small table thumbnails and recipient cards still crop to fill, by design. Verified in headless Chromium with a test image: an 800x600 photo rendered uncropped at 560x420 (desktop) and 350x263 (390 px-wide mobile viewport).

### Remaining tasks / known limits
* Run the checklist above (nothing PHP-side has been executed yet).
* `.htaccess` needs `AllowOverride All` (XAMPP's default for `htdocs`). If images return HTTP 500, that directive is restricted; check `httpd.conf`. On non-Apache servers (nginx, IIS) the equivalent rules must be set in the server config.
* Uploaded images are publicly readable by URL (names are unguessable, but there is no login check on the file itself).
* A crash between saving a file and the database commit could leave an orphan file (normal failures are cleaned up).
* No resizing, thumbnails or EXIF stripping; there is no "remove photo" without replacing it.
* Volunteer pages and the feedback page still show the emoji only.
* No mock-data fallback exists (see above); restoring one would be a separate task.
